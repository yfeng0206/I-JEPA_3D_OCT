perf(guides): memmap fast path - the guide cache was the bottleneck

The run is 2.5x slower per epoch than the rectangle baseline (10,865s vs
4,375s) despite MIRAGE being frozen AND precomputed, so nothing of MIRAGE runs
at train time. Measured cause: np.savez_compressed keeps one deflate stream
per array, so reading a SINGLE slice inflates the whole (100,2,200,200)
volume -- 8 MB of decompression to serve 80 KB, 600,000 times per epoch.

Measured on the live cache (random volumes, cold):
  compressed npz            35.1 ms/slice  -> 0.98 h/epoch across 6 workers
  memmap .npy, reopened      9.6 ms/slice  -> 0.27 h/epoch
  memmap .npy, cached handle  0.7 ms/slice -> ~0.03 h/epoch

Diagnosis is consistent with the symptom: GPU utilisation samples at 0/1/97/
100/99/100/1/92/100/100 %% and CPU at 21%% of 16 cores -- neither saturated,
so the loop was I/O bound, not compute bound. It also explains the envelope
vs anatomy gap: the envelope guide cache is 0.15 GB of 1-bit envelopes
against 3.6 GB of two-channel soft scores, 28x more data per read.

Adds convert_guides_to_npy.py (CPU/IO only, no GPU, resumable, verifies
written volumes against their source) and a loader fast path that memmaps the
.npy and caches the handle per worker, bounded at 256 handles. Provenance
validation is preserved via a sidecar .json and factored into _check_stamp so
both paths enforce it identically.

Verified: fast path is byte-identical to the compressed path across 32
volume/slice pairs, and 28x faster. 117 tests pass. Falls back to .npz when
no .npy is present, so existing caches keep working untouched.

Trade: ~48 GiB uncompressed against 3.6 GiB, on a disk with 870 GiB free.

NOT yet deployed - the running job is untouched.
